# Релизы macOS

Workflow `.github/workflows/release.yml` запускается при появлении в GitHub тега вида
`v1.2.3`. Поддерживаются предварительные версии, например `v1.3.0-beta.1`: они
публикуются с отметкой prerelease. Другие теги не создают релиз приложения.

Сначала добавь workflow и скрипты в коммит, который будет отмечен тегом, и отправь
его в GitHub. Затем создай и отправь версионный тег на этот коммит. Локальное
создание тега без отправки в GitHub не запускает Actions. Новый релиз — новый тег;
не перемещай теги опубликованных версий. Actions должны быть разрешены в репозитории.

## Что делает workflow

1. Запускает тесты и собирает приложение отдельно на Apple Silicon и Intel.
2. Берёт номер версии из тега, номер сборки — из номера запуска Actions; записывает
   их в `Info.plist` до подписи приложения.
3. Проверяет локальную подпись и архитектуру, создаёт ZIP, DMG и SHA-256 для каждой
   архитектуры.
4. После успешного завершения обеих сборок создаёт draft release, загружает файлы
   и публикует его. Если загрузка не удалась, релиз остаётся черновиком.

Используются [стандартные runner macOS 26](https://github.blog/changelog/2026-02-26-macos-26-is-now-generally-available-for-github-hosted-runners/):
`macos-26` для arm64 и `macos-26-intel` для x86_64. Это два отдельных приложения,
не один universal binary. Все Actions закреплены по SHA коммита.

Для публикации используется встроенный `GITHUB_TOKEN`, отдельный персональный
токен не нужен. Доступ `contents: write` выдан только job публикации. Этот токен
не может обходить ограничения организации или политики репозитория.

## Файлы релиза

Для тега `v1.2.3`:

- `Obeshchal-v1.2.3-macos-arm64.zip`, `.dmg` и `.sha256`;
- `Obeshchal-v1.2.3-macos-x86_64.zip`, `.dmg` и `.sha256`.

ZIP сохраняет структуру `.app` и права на исполняемый файл. В DMG находятся только
приложение и ссылка на Applications. Кеши сборки и личное хранилище обещаний в
архивы не попадают. Установщик работает без прав администратора, если пользователь
копирует приложение в доступный ему каталог.

Повторный запуск workflow может дозагрузить файлы в оставшийся draft. Уже
опубликованный релиз автоматически не перезаписывается. При сбое сборки или
тестов публикация не начинается.

## Локальная проверка

```sh
make check
RELEASE_TAG=v1.2.3 make package
```

Пакеты появятся в `dist/release/` для архитектуры текущего Mac. Ничего не
отправляется в GitHub. Номер сборки при необходимости можно задать через
`APP_BUILD_NUMBER=123`. Команда `make package` сама собирает приложение с версией
из тега. Для проверки контрольных сумм:

```sh
cd dist/release
shasum -a 256 -c Obeshchal-v1.2.3-macos-arm64.sha256
```

## Подпись Apple

Сейчас приложение подписывается ad hoc. Developer ID и нотариализация не
настроены: для них понадобятся сертификат и доступ к Apple Developer. Поэтому
Gatekeeper может предупредить пользователя при запуске скачанного приложения.
Упаковка в DMG этого не меняет. [Объяснение Apple](https://support.apple.com/102445).

Сборки проверяются на macOS 26; запуск на минимально поддерживаемой macOS 14
отдельно в этом workflow не проверяется.
